# ADR-002：分离 Agent、确定性节点与外部工具职责

- 状态：Accepted
- 日期：2026-08-20

## 背景

模型擅长从中文需求提取含义、比较开放式偏好和提出候选修复，但不适合作为金额计算器、数据库或 API 真实性边界。把每项功能都命名为 Agent 会增加不可控决策点，也让面试中的架构解释失去可信度。

## 候选方案

1. 景点、天气、预算、路线、酒店全部实现为自主 Agent；
2. 只有语义决策使用 Agent，外部查询与可验证规则使用受限工具或普通节点；
3. 完全不用模型，只做规则式表单规划。

## 决策

采用方案 2，并按以下边界实现：

| 类型 | 负责 | 不负责 |
|---|---|---|
| Agent 节点 | 约束抽取、候选比较、排程提案、语义修复 | 价格真实性、金额求和、硬规则最终裁决 |
| 确定性节点 | 预算计算、时间/距离检查、冲突分类、状态持久化、repair routing | 编造用户偏好或开放式推荐理由 |
| 外部工具 | POI、天气、路线等数据读取 | 自行改变计划或放宽硬约束 |

所有外部输入先通过 schema 校验和 normalizer。硬约束失败时，图只能返回冲突或请求用户批准放宽，不允许 Agent 静默删除条件。

## 后果

- Agent 数量由问题边界决定，而不是简历包装需要。
- 普通代码测试可以覆盖预算、重复地点和数据来源等关键风险。
- 需要维护清楚的输入/输出契约，否则 Agent 与 deterministic node 之间仍会通过松散文本耦合。

## 重新评估条件

只有当固定评测证明某个确定性步骤需要语义推理，且 schema、权限和失败策略明确时，才允许把它升级为 Agent 节点。
