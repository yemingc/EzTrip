# ADR-005：使用版本化 Pydantic 契约统一领域边界

- 状态：Accepted
- 日期：2026-08-20

## 背景

旅行请求会经过 Agent、外部 provider、确定性预算/校验节点、LangGraph state 和未来前端 API。如果各节点用自由文本或私有字典传递数据，字段漂移会让来源、金额和修复责任无法稳定测试，也会让模型输出被误当成业务事实。

## 候选方案

1. 每个 Agent 自行定义输入输出字典；
2. 只在 FastAPI 边界定义请求/响应 DTO，图内部继续传松散对象；
3. 建立版本化 Pydantic 领域契约，由 API、图节点和 provider normalizer 共同消费，并机械导出 JSON Schema。

## 决策

采用方案 3。V1 契约遵守以下规则：

- 所有公开模型拒绝未知字段，并使用 `schema_version=1.0` 标记顶层对象；
- 旅行范围固定为中国单城市 2–5 天，预算币种固定为 CNY；
- 金额使用 Decimal 语义，区间和估算必须显式标记；
- provider 数据携带来源、数据模式、获取时间和可选原始响应哈希；
- 天气风险只能由 live/fixture 天气数据生成；
- 住宿候选不表达实时房态、可预订性或未经授权的实时价格；
- 行程时间线、费用引用、版本血缘和修复动作在模型层执行跨字段校验；
- 提交生成后的 JSON Schema bundle 和可解析示例，CI 检查它们与代码一致。

`PlannerContext` 已在 `EZ-006` 中作为独立契约实现，并由确定性编译器从 `TripRequest` 生成。它只包含日期、人数、预算参考尺度、约束作用域、澄清项和能力就绪状态；候选与天气等 provider 结果仍在后续节点获取，避免把尚未验证的外部事实塞进请求解释。规则和门禁见 [`docs/planning/planner-context.md`](../planning/planner-context.md)。

## 后果

- Agent 输出必须先通过 schema，错误会在进入预算或排程前暴露；
- 确定性规则获得稳定输入，可进行普通单元测试；
- 新字段需要显式版本与兼容性判断，开发速度略慢但证据更可靠；
- JSON Schema bundle 是代码生成物，禁止手工修改后绕过模型。

## 重新评估条件

当出现多城市、外币、授权酒店库存或公开 API 兼容性要求时，新增契约版本并提供迁移策略，不在 V1 上静默改变语义。
